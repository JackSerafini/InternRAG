# Indexing Pipeline

The indexing pipeline is responsible for transforming the existing SEM dataset into a searchable representation stored in Qdrant.

There are currently **two distinct indexing-related systems** in the repository:

1. **Generic document indexing prototype**: it is implemented through `upload/` and `pipeline_wrappers/indexing/`. This was an early experiment for building a RAG system capable of growing its knowledge base through user-uploaded documents. It works with formats such as PDF, DOCX, PPTX, HTML, Markdown, and TXT and is described separately in the [Kubernetes documentation](../k8s/README.md)
2. **SEM dataset indexing pipeline**: it is implemented through `notebooks/embed.ipynb` and `src/sem_rag/qdrant_upload.py`. This is the indexing pipeline relevant to the current InternRAG system and is the focus of this document

The second pipeline operates on the existing, static SEM dataset. It performs the domain-specific processing required to represent SEM images together with their associated microscope metadata and stores the resulting representations in Qdrant.

## Overview

The SEM indexing process can be summarized as:

```text
        SEM Dataset
             │
     ┌───────┴───────┐
     │               │
   Images         Metadata
     │               │
     ▼               ▼
Embeddings     Metadata Processing
     │               │
     └───────┬───────┘
             │
             ▼
     Haystack Documents
             │
             ▼
          Qdrant
```

The main stages are:

1. Load the SEM dataset
2. Process the image data
3. Load or generate image embeddings
4. Process the associated metadata
5. Construct Haystack `Document` objects
6. Store the resulting documents and embeddings in Qdrant

The main implementation is distributed between `notebooks/embed.ipynb` and `src/sem_rag/qdrant_upload.py`: the notebook is primarily used for experimentation and embedding generation, while `qdrant_upload.py` contains the functionality for constructing the documents and uploading them to Qdrant.

## Input Data

The indexing pipeline operates on SEM images together with their associated acquisition and microscope metadata.  
The metadata describes the conditions under which each image was acquired. Examples include:

* Working distance
* Beam time
* Stage position
* Accelerating voltage
* Magnification-related parameters

Each image is associated with a unique `SEMImageID`, which is used to associate the image, its embedding, and its metadata throughout the indexing process.

The dataset is treated as a **static knowledge base**. The current pipeline is therefore focused on preparing the existing dataset rather than providing a general-purpose mechanism for continuously adding new SEM samples.

## Image Embeddings

Each SEM image is represented by an embedding vector generated by an image embedding model.

InternRAG currently supports different embedding spaces for experimentation. In particular, Qwen-based and DINO-based embeddings have been explored. The two representations are kept in separate Qdrant collections (*SEMImages_qwen* and *SEMImages_dino*) because they have different dimensions (respectively, 4096 and 768) and represent the images in different embedding spaces.

Each embedding is associated with the corresponding SEM image through its `SEMImageID`.  
The embedding provides the vector representation used during semantic similarity retrieval.

## Metadata Processing

In addition to the image embedding, the pipeline extracts and stores relevant SEM metadata.  
The metadata fields are defined centrally in the project configuration. The current set includes:

```text
AP_WD
AP_FREE_WD
AP_BEAM_TIME
AP_STAGE_LOW_Z
AP_STAGE_CENTRE_X
AP_C3
AP_EHT_CAL_30KV
AP_EHT_CAL_10KV
AP_EHT_CAL_100
AP_EHT_CAL_24KV
AP_MINMAG
```

These fields describe acquisition and microscope parameters associated with each image.  
Numeric metadata is stored in Qdrant as structured payload fields. This allows the retrieval pipeline to apply metadata filters when appropriate.  
The metadata therefore complements the image embedding:

```text
Image
  │
  └── Embedding ──→ Semantic similarity

Metadata
  │
  └───────────────→ Metadata filtering
```

The two mechanisms are used together during retrieval, but they serve different purposes: the embedding represents the visual/semantic content of the image, while the metadata represents structured information about its acquisition conditions.

## Haystack Documents

The indexed samples are represented as Haystack `Document` objects before being uploaded to Qdrant.  
Conceptually, each document contains:

```text
Document
├── id
├── content
├── embedding
└── meta
    ├── SEMImageID
    ├── AP_WD
    ├── AP_BEAM_TIME
    ├── ...
    └── other metadata
```

The main components are:

* `id`: identifies the indexed sample
* `content`: textual representation of the sample and its metadata
* `embedding`: vector representation of the SEM image
* `meta`: structured metadata stored as Qdrant payload

The textual content provides a human-readable representation of the indexed sample, while the embedding and structured metadata are used by the retrieval system.

## Qdrant

Qdrant is used as the vector database for the indexed SEM dataset.

For each indexed sample, the image embedding is stored as the vector representation and the associated metadata is stored as payload.

The project uses separate collections for different embedding spaces (e.g.: *SEMImages_dino*, *SEMImages_qwen*). This separation allows the embedding models to be evaluated independently without mixing vectors with incompatible dimensions or representations.

The metadata fields used for filtering are also indexed in Qdrant so that structured constraints can be applied efficiently during retrieval.

## Indexing Workflow

The current static-dataset workflow can be divided into two main parts:

1. Embedding generation: `notebooks/embed.ipynb` is used to work with the image embeddings. It loads the SEM image data and generates or processes the embeddings required by the retrieval system
2. Qdrant upload: `src/sem_rag/qdrant_upload.py` is responsible for constructing the Haystack documents and uploading them to Qdrant

The general workflow is:

```text
SEM images + metadata
        │
        ▼
 Load embeddings
        │
        ▼
 Build metadata
        │
        ▼
 Build Haystack Documents
        │
        ▼
 Create / Configure Qdrant collection
        │
        ▼
 Upload documents
```

This produces the static knowledge base used by the retrieval pipeline.

## Development and Experimentation

Several notebooks in the repository were used during the development and evaluation of the indexing process.
Relevant notebooks include:

* `notebooks/embed.ipynb`: embedding generation and experimentation
* `notebooks/qdrant_upload.ipynb`: experiments related to uploading data to Qdrant
* `notebooks/qdrant_analysis.ipynb`: analysis of the resulting Qdrant collections
* `notebooks/test_data.ipynb`: inspection and experimentation with the dataset

These notebooks were used to validate individual components and experiment with different representations before consolidating the indexing functionality in `src/sem_rag/qdrant_upload.py`.

After indexing, every SEM sample has a searchable representation consisting of an image embedding and structured metadata:

```text
                SEM Sample
                    │
          ┌─────────┴─────────┐
          │                   │
        Image              Metadata
          │                   │
          ▼                   ▼
      Embedding        Structured payload
          │                   │
          ▼                   ▼
  Vector similarity    Metadata filtering
          │                   │
          └─────────┬─────────┘
                    │
                    ▼
                 Qdrant
```

This representation forms the static SEM knowledge base used by the retrieval pipeline.
